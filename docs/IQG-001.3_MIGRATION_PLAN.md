# IQG-001.3 — Plan Maestro de Migración V11 → IQ GROWTH

**Estado:** diseño previo a implementación  
**Fecha:** 2026-09-11  
**Autoridad:** Iván Quea, CEO  
**Arquitectura/coordinación:** ChatGPT  
**Implementación futura:** Codex  
**Challenge de producto:** Claude  
**Auditoría de integridad/seguridad:** DeepSeek

---

## 1. Objetivo

Migrar la información útil y verificable de VANSAM POS V11 hacia IQ GROWTH sin convertir defectos del legado en hechos falsos del nuevo sistema.

La migración debe preservar la historia, permitir reconciliación y ser repetible, auditable e idempotente.

**Regla central:** IQG-001.3 no es una copia de Firebase a PostgreSQL. Es un proceso ETL forense con reglas explícitas de autoridad por dominio.

---

## 2. Principios obligatorios

1. **Historia Sagrada:** no inventar ni reescribir hechos históricos.
2. **Aislamiento:** todo dato migrado pertenece a una empresa y sucursal explícitas.
3. **Trazabilidad:** todo registro migrado debe poder relacionarse con su origen V11.
4. **Idempotencia:** ejecutar la misma migración dos veces no debe duplicar datos.
5. **No sobreinterpretación:** un dato que V11 no puede probar queda como desconocido/no verificable.
6. **Separación núcleo/vertical:** recetas, toppings y preparación gastronómica no deben deformar el núcleo universal.
7. **PII mínima:** no guardar en Git información real de clientes, teléfonos, direcciones, identificadores fiscales ni secretos.

---

## 3. Restricción financiera crítica

V11 no implementa pagos reales ni caja conciliable. Por tanto:

- un `pedido` V11 **NO prueba un pago**;
- un total de pedido V11 **NO debe migrarse como efectivo/QR/tarjeta cobrado**;
- no se crearán pagos históricos ficticios;
- no se reconstruirá una caja histórica inexistente;
- los pedidos legacy podrán convertirse en operaciones históricas, pero su estado financiero debe quedar explícitamente como **NO VERIFICABLE DESDE V11** o equivalente compatible con el modelo definitivo.

Si el esquema final no puede representar esta incertidumbre de forma correcta, la implementación debe detenerse y abrir una decisión de arquitectura antes de importar.

## 4. Fuentes V11 conocidas

La auditoría forense identificó estas fuentes:

| Fuente V11 | Contenido | Autoridad propuesta | Riesgo |
|---|---|---|---|
| `pedidos/<num>` en Firebase RTDB | pedidos activos/históricos usados por la UI | Primaria para pedidos existentes al snapshot | número no es ID durable; posibles sobrescrituras/concurrencia |
| `historial/<num>` | copia de pedido al crear | Corroborativa, no una segunda operación | no se actualiza al cambiar estados; puede divergir |
| `clientes/wsp_<entrada>` | datos CRM y agregados | Primaria para perfil legacy; agregados deben validarse/recalcularse | teléfono usado como clave mutable/PII |
| `satisfaccion/sat_<ms>` | rating 1–5 + comentario | Primaria para satisfacción si se conserva | no tiene vínculo estable a pedido |
| `config/stock` RTDB | saldo/ajustes manuales | Una de varias fuentes; requiere reconciliación | consumos de venta pueden existir solo localmente |
| `vs_stock` localStorage | stock por navegador | Evidencia de terminal, no autoridad universal | divergencia entre terminales |
| `config/insumos`, `config/gramos` RTDB | costos/gramajes | Configuración vigente al snapshot | sin historial/versionado |
| `vs_costos` localStorage | costos/gramajes locales | Evidencia de terminal | posible divergencia con RTDB |
| HTML V11 | catálogo, precios embebidos, recetas nominales, extras | Fuente de configuración del software auditado | no prueba vigencia histórica de cada precio |
| variables de delivery | tarifas temporales | No migrar como hecho histórico | no persistidas |
| reportes/cierre V11 | cálculos derivados | NO usar como fuente de verdad | mezclan pedidos con ventas/caja y no filtran correctamente |
| contraseña/admin visual | pseudo-control de acceso | NO migrar | no representa usuario/identidad real |

La copia auditada de V11 queda tratada como artefacto de evidencia con SHA-256:

`4bec220566ca90c86ace9b82e3978d12cf7d82cfa83f2d131bbed1cada107aac`

## 5. Regla de autoridad por dominio

### 5.1 Pedidos

Autoridad primaria: `pedidos/<num>` del snapshot de RTDB.

`historial/<num>` se usa únicamente para:
- detectar diferencias;
- recuperar evidencia complementaria cuando sea inequívoca;
- identificar posibles pedidos faltantes en una fuente.

Nunca se importan `pedidos/<num>` y `historial/<num>` como dos operaciones distintas sin demostrar que representan eventos diferentes.

### 5.2 Clientes

Autoridad primaria: colección `clientes`.

Reglas:
- generar UUID técnico nuevo;
- cifrar/minimizar PII según política IQ GROWTH;
- conservar relación con la clave legacy mediante registro técnico de migración, no usando el teléfono como PK;
- los campos agregados como visitas/gasto deben **recalcularse desde operaciones migradas cuando sea posible**;
- si el agregado legacy no puede reproducirse, se conserva como evidencia del snapshot, no como verdad recalculada del nuevo sistema.

### 5.3 Inventario

No existe una única fuente fiable en V11.

Antes del cutover deben capturarse:
- `config/stock` RTDB;
- `vs_stock` de cada terminal activa;
- timestamp, identificador de terminal y hash de cada captura.

Las divergencias se reportan. No se inventa un historial de movimientos que V11 nunca registró.

El saldo aceptado para iniciar IQ GROWTH se ingresa como **movimiento de apertura/ajuste de migración**, con motivo y evidencia de origen.

### 5.4 Costos y gramajes

RTDB y localStorage se comparan por terminal.

La migración de configuración vigente se hace con fecha de corte. No se retroconstruye un historial de costos inexistente.

### 5.5 Catálogo y precios

El HTML V11 puede servir para sembrar catálogo actual y precios conocidos por esa versión.

Reglas:
- productos → `elemento` o entidad correspondiente;
- precio actual conocido → `precio_vigente` desde fecha de migración/cutover, salvo que exista evidencia temporal mejor;
- precios históricos vendidos deben provenir de las líneas del pedido histórico, no del precio vigente actual;
- no backdatear precios de catálogo sin evidencia.

### 5.6 Recetas/toppings/preparación

Son vertical VANSAM.

No deben introducir campos pizza-específicos en el núcleo. Se conservan como insumo para IQG-002/VANSAM vertical.

### 5.7 Satisfacción

Si el núcleo actual no tiene una entidad compatible sin deformación semántica, los registros se mantienen en staging/quarantine hasta que exista el contrato de producto correspondiente.

No se fuerza un rating a una tabla incorrecta solo para “migrar todo”.

## 6. Mapa origen → destino preliminar

| Origen | Destino IQ GROWTH | Regla |
|---|---|---|
| empresa VANSAM implícita | `iqg_core.empresa` | crear tenant VANSAM explícito una vez |
| local VANSAM implícito | `iqg_core.sucursal` | crear sucursal explícita una vez |
| producto/menu | `iqg_core.elemento` | UUID nuevo + referencia legacy técnica |
| precio actual embebido | `iqg_core.precio_vigente` | vigencia desde cutover si no hay fecha histórica fiable |
| pedido V11 | `iqg_core.operacion` | preservar clave/número legacy como referencia; jamás como PK |
| ítems del pedido | `iqg_core.operacion_linea` | preservar descripción, cantidad, precio y subtotal originales cuando existan |
| estado `pendiente/listo` | estado/operacion_estado compatible | mapear únicamente semántica demostrable; no inferir entrega/cobro |
| cliente | `iqg_core.cliente` | UUID nuevo; PII cifrada/minimizada |
| cliente copiado dentro del pedido | referencia/corroboración | resolver contra cliente cuando sea inequívoco; no duplicar por defecto |
| pago | **sin fuente V11 confiable** | NO crear pagos históricos ficticios |
| caja | **sin fuente V11 confiable** | NO crear movimientos/cierres históricos ficticios |
| stock aceptado al corte | `iqg_core.movimiento` | movimiento de apertura de migración, no historia inventada |
| satisfacción | staging/vertical futura | preservar hasta contrato definitivo |
| recetas/gramajes | vertical VANSAM / staging | fuera del núcleo universal |

**Nota:** los nombres de columnas exactos deben validarse contra el schema resultante de IQG-001.2 antes de Codex implementar el importador.

## 7. Arquitectura del ETL

```text
V11 PRODUCCIÓN
    │
    ├── RTDB export JSON
    ├── localStorage por terminal
    └── artefacto HTML/hash
            │
            ▼
      SNAPSHOT INMUTABLE
            │
            ▼
      STAGING V11 AISLADO
            │
    ┌───────┼─────────┐
    ▼       ▼         ▼
 VALIDAR  NORMALIZAR  QUARANTINE
    │       │         │
    └───────┴────┬────┘
                 ▼
          MAPEO LEGACY→UUID
                 │
                 ▼
          IMPORTACIÓN IQG
                 │
                 ▼
          RECONCILIACIÓN
                 │
        PASS ─────┴───── FAIL
         │                 │
         ▼                 ▼
       COMMIT           ROLLBACK
```

### Staging

El importador debe usar un área de staging separada del núcleo. Puede ser schema temporal/migration-only o base efímera, pero no debe convertir tablas legacy en parte permanente del dominio universal.

### Registro técnico de migración

Debe existir durante el proceso un registro equivalente a:

- `migration_run_id`
- `source_system = VANSAM_V11`
- `source_object`
- `legacy_key`
- `source_hash`
- `target_table`
- `target_id`
- `status`
- `error_code`
- `imported_at`

Con unicidad por fuente/objeto/clave/hash o estrategia equivalente que garantice idempotencia.

## 8. Captura de evidencia — Fase 0

Antes de cualquier transformación real:

1. Exportar RTDB completo autorizado de VANSAM V11.
2. Capturar `vs_stock` y `vs_costos` de **cada terminal activa**.
3. Registrar por captura:
   - fecha/hora;
   - dispositivo/terminal;
   - origen;
   - SHA-256;
   - tamaño;
   - responsable.
4. Conservar hash del HTML V11 auditado.
5. No almacenar dumps reales con PII, credenciales o secretos en Git.
6. Git solo debe contener:
   - manifiestos sin PII;
   - hashes;
   - scripts;
   - documentación;
   - fixtures sintéticos.

Los datos reales deben quedar en almacenamiento autorizado y cifrado fuera del repositorio.

---

## 9. Normalización

### 9.1 Identificadores

Nunca reutilizar `num` de pedido, teléfono o timestamp como PK nuevo.

Todos los objetos nuevos reciben UUID del sistema destino.

### 9.2 Fechas

Preservar timestamp legacy cuando existe como **fecha histórica declarada por la fuente**.

Registrar por separado la fecha de importación del servidor.

No sustituir fecha histórica con “ahora”.

Si una fecha no existe o es ambigua, queda NULL/desconocida o en quarantine según el contrato; no se inventa.

### 9.3 Teléfonos/WhatsApp

Normalización determinista y conservadora.

- eliminar ruido de formato solo cuando no cambia semántica;
- no asumir país/código internacional cuando el dato sea ambiguo;
- deduplicar solo con criterio reproducible;
- casos ambiguos → quarantine/revisión, no merge destructivo.

### 9.4 Dinero

Usar decimal exacto, nunca float.

Guardar valor original y resultado normalizado durante staging para poder explicar cualquier diferencia.

### 9.5 Estados

V11 prueba principalmente `pendiente` y `listo`.

No inferir:
- entregado;
- pagado;
- cancelado;
- reembolsado;
- despachado;

si la fuente no lo demuestra.

## 10. Reconciliación obligatoria

Cada corrida produce un reporte firmado por hashes de entrada y versión del importador.

### Pedidos

- total de claves `pedidos` observadas;
- total importadas;
- total quarantine;
- total duplicadas/correlacionadas con `historial`;
- **ecuación obligatoria:** origen = importadas + quarantine + duplicados explicados.

No puede haber filas “desaparecidas”.

### Montos

Comparar:
- suma de `pedido.total` fuente;
- suma de totales de operaciones legacy destino;
- diferencias por pedido;
- diferencia acumulada.

Una diferencia no se corrige silenciosamente recalculando. Se reporta.

**Esta reconciliación es de importe de pedidos, NO de pagos/caja.**

### Líneas

Por pedido:
- cantidad de líneas;
- cantidades;
- precios unitarios originales;
- subtotales si existen;
- total declarado.

Diferencias entre líneas y total se preservan/reportan como calidad de fuente; no se reescribe el pasado para hacer cuadrar.

### Clientes

- registros fuente;
- clientes únicos normalizados;
- merges deterministas;
- ambiguos;
- sin teléfono/PII inválida;
- referencias pedido→cliente resueltas/no resueltas.

### Estados

Conteo por estado V11 antes/después del mapping.

### Inventario

Reporte por insumo:
- RTDB;
- localStorage por terminal;
- divergencia;
- saldo de apertura finalmente aprobado;
- motivo de decisión.

---

## 11. Quarantine

Ningún dato dudoso debe provocar invención.

Ejemplos:
- pedido sin estructura parseable;
- total inválido;
- timestamp corrupto;
- cliente ambiguo;
- teléfono imposible de normalizar sin asumir;
- producto no mapeable;
- divergencia fuerte de inventario.

Cada fila quarantine debe tener:
- source object/key;
- código de error;
- explicación;
- payload hash;
- severidad;
- acción requerida.

No guardar PII cruda en logs de Git/CI.

---

## 12. Idempotencia

Prueba obligatoria:

1. importar snapshot A;
2. registrar conteos/UUIDs;
3. importar exactamente snapshot A de nuevo;
4. verificar:
   - 0 operaciones duplicadas;
   - 0 clientes duplicados por la segunda corrida;
   - 0 movimientos de apertura duplicados;
   - mappings estables;
   - reporte que marque reintento/idempotencia.

---

## 13. Estrategia de paralelo y cutover

### Etapa A — Shadow import

- V11 continúa siendo producción.
- IQ GROWTH recibe copia de datos en ambiente de prueba.
- No escribe de vuelta a V11.
- Se ejecuta reconciliación completa.

### Etapa B — Segundo snapshot/delta

Como V11 no tiene CDC robusto ni historial inmutable, el delta se calcula por clave + hash entre snapshots.

- nuevos objetos → importar;
- objeto igual → ignorar;
- objeto cambiado → tratar según semántica; nunca sobrescribir historia sin evidencia;
- clave desaparecida/sobrescrita → reportar, no inventar.

### Etapa C — Ventana de corte

Para minimizar carreras:

1. detener nuevas operaciones V11 durante ventana controlada;
2. snapshot final RTDB + terminales;
3. ejecutar delta final;
4. reconciliar;
5. activar IQ GROWTH solo si todos los gates críticos pasan.

### Etapa D — V11 read-only

Conservar V11 como evidencia/consulta por periodo definido. No borrarla inmediatamente.

---

## 14. Rollback

### Antes de producción

Ambiente efímero → descartar y recrear.

### Cutover final

Preferencia: staging + importación transaccional donde sea viable. Si falla gate crítico antes del COMMIT, rollback completo.

Una vez que una importación válida se confirme en el dominio append-only:
- no borrar historia para “deshacer”;
- correcciones posteriores deben ser eventos/migraciones compensatorias trazables;
- nunca UPDATE destructivo para ocultar error de migración.

## 15. Criterios GO para IQG-001.3

Todos los siguientes deben cumplirse:

1. snapshot RTDB identificado y hasheado;
2. snapshots de terminales relevantes identificados y hasheados;
3. 100% de pedidos fuente contabilizados como importados/quarantine/duplicados explicados;
4. 0 duplicados generados por reejecución;
5. diferencia de suma de importes de pedidos = 0 o diferencias individualizadas y formalmente aceptadas;
6. ningún pago histórico ficticio;
7. ninguna caja histórica ficticia;
8. fechas legacy preservadas cuando existen;
9. precios históricos de líneas preservados;
10. customer mapping reproducible;
11. PII fuera de Git/logs públicos;
12. aislamiento VANSAM company/branch validado;
13. prueba de segunda corrida idempotente PASS;
14. prueba de rollback PASS;
15. prueba 2 company × 2 branch sin fugas PASS;
16. reporte de reconciliación generado;
17. DeepSeek no identifica P0/P1 de integridad en el importador;
18. ChatGPT confirma alineación con los cinco principios.

---

## 16. Criterios NO-GO

Detener cutover si ocurre cualquiera:

- faltan exports de una fuente relevante;
- hay pedidos sin contabilizar;
- el importador convierte pedidos en pagos sin evidencia;
- se pierden fechas o precios históricos;
- existen duplicados no explicados;
- el importador no es idempotente;
- hay PII/secrets en Git o logs;
- falla aislamiento entre tenants/sucursales;
- rollback no está demostrado;
- inventario inicial se decide silenciosamente ante fuentes divergentes;
- el core necesita cambios pizza-específicos para aceptar datos V11;
- existe un P0/P1 abierto que pueda corromper historia o mezclar tenants.

---

## 17. Lo que NO se migrará como verdad

- contraseña administrativa de V11;
- pseudo-roles de pantalla;
- reportes “del día” derivados incorrectamente;
- cierre/caja calculados por UI;
- supuesto de que cada pedido fue pagado;
- supuesto de que `listo` significa entregado;
- historial de inventario reconstruido artificialmente;
- tarifas delivery no persistidas;
- visitas/gasto CRM sin contraste cuando puedan recalcularse;
- cualquier dato inferido únicamente porque “debería haber ocurrido”.

6. ¿Existen claves de pedido sobrescritas por colisión?
7. ¿Qué campos exactos de cliente existen en producción versus los definidos por el HTML?
8. ¿Qué porcentaje de pedidos puede asociarse inequívocamente con un cliente?
9. ¿Hay datos de satisfacción útiles que valga la pena preservar?
10. ¿Cuál será el saldo de inventario oficial de apertura en la fecha de cutover?

Estas preguntas no se responden por suposición. Se resuelven en Fase 0 mediante snapshot autorizado.

## 21. Decisión arquitectónica propuesta

**IQG-001.3 debe tratar V11 como una fuente legacy imperfecta, no como verdad empresarial absoluta.**

La meta no es que IQ GROWTH “se vea igual” a V11. La meta es preservar todo hecho demostrable, identificar explícitamente lo que V11 no puede demostrar y comenzar la nueva historia con garantías superiores desde el instante del cutover.
