## 2. Hallazgos aceptados como requisitos

### A1 — Riesgo de degradación CRM antes del snapshot

La auditoría Codex ya identificó que compras/ediciones CRM pueden borrar campos y que cambiar teléfono puede perder o combinar perfiles.

**Decisión:** antes del snapshot definitivo debe existir una estrategia de preservación. No se modificará V11 productivo sin autorización expresa del CEO.

Opciones válidas a evaluar:
1. parche mínimo y probado de preservación de campos;
2. congelar edición de clientes durante ventana de preservación;
3. exportar RTDB completo antes de cualquier modificación;
4. combinación de las anteriores.

No se declara pérdida real ocurrida sin evidencia de datos de producción; se declara **riesgo estático confirmado**.

### A2 — Pedido legacy no equivale a venta cobrada

Se confirma la regla existente del plan:
- no crear pagos históricos;
- no reconstruir caja histórica;
- `pedido.total` representa importe declarado del pedido, no cobro confirmado;
- estado financiero legacy = desconocido/no verificable.

Esto ya queda resuelto por Historia Sagrada; no requiere una nueva decisión CEO.

### A3 — `historial/` es fuente corroborativa, no autoridad primaria

Se confirma:
- `pedidos/` es autoridad primaria para el snapshot observado;
- `historial/` se conserva como evidencia de divergencia;
- no se interpreta su estado como estado final del pedido;
- nunca se importan ambas rutas como dos operaciones distintas sin prueba.

### A4 — Colisiones de `num` impiden usarlo como identidad

Se confirma:
- `num` nunca será PK ni clave única de idempotencia;
- continuidad de numeración no sirve para probar integridad histórica;
- el importador debe detectar duplicidad/divergencia por snapshot, ruta, payload y hash.

### A5 — Stock histórico no es reconstruible

Se confirma:
- no crear kardex histórico V11;
- capturar RTDB + `vs_stock` de cada terminal;
- saldo aceptado al corte entra como movimiento de apertura/migración;
- cualquier divergencia queda documentada.

### A6 — Costos y márgenes históricos no son hechos confiables

Se confirma:
- no importar margen histórico calculado con costos vigentes al momento del snapshot;
- no recalcular rentabilidad pasada con precios actuales;
- costos/gramajes legacy pueden servir como configuración de corte, no como historia sellada.

### A7 — Delivery: conservar evidencia, no fabricar ingreso

Se acepta el hallazgo de que la tarifa delivery no forma parte de `pedido.total` de manera confiable.

**Se rechaza** reconstruir automáticamente ingreso histórico como `total + tarifaDelivery`.

Regla integrada:
- conservar `pedido.total` original;
- si existe evidencia inequívoca por pedido de un cargo de delivery, guardarlo en staging como `reconstructed/low-confidence` o equivalente;
- nunca convertir ese cargo reconstruido en pago confirmado;
- si no existe evidencia transaccional suficiente, no sumarlo al importe histórico.

### A8 — Fechas CRM no son autoridad temporal

Se confirma:
- timestamps de pedidos se conservan como tiempo legacy declarado por la fuente;
- fechas localizadas de cliente (`DD/MM/YYYY`) no se usan como reloj autoritativo;
- primera/última interacción se recalcula desde operaciones cuando sea posible;
- anomalías se marcan, no se corrigen silenciosamente.

### A9 — Teléfono no es identidad de persona

Se confirma:
- UUID técnico nuevo para cliente/persona;
- teléfono es atributo PII, no PK;
- no fusionar automáticamente personas solo por compartir número;
- coincidencias ambiguas → revisión/quarantine.

### A10 — Agregados CRM no son hechos primarios

Campos como `visitas`, `ticketPromedio`, `totalGastado`, `ultimoProducto`, `ultimoTamano` no se importan como métricas autoritativas.

Tratamiento:
- recalcular desde operaciones cuando sea posible;
- conservar snapshot original como evidencia si aporta valor;
- `ultimoProducto` no se convierte en producto favorito.

### A11 — Catálogo legacy necesita identidad congelada

No depender de nombre visible para reconciliar productos en runtime.

El staging debe crear identidad legacy reproducible por registro/configuración observada y conservar descripción original. Renombres, emojis, mitad-y-mitad y variantes P/M/G pertenecen al vertical VANSAM o a atributos configurables, no al núcleo.

### A12 — Satisfacción sin pedido queda desacoplada

No forzar `satisfaccion/` a una relación por pedido inexistente.

Conservar como serie legacy/staging y solo migrar a un contrato definitivo si su semántica es compatible.

### A13 — Estados antiguos son ambiguos

No mapear `pendiente`/`listo` a entregado, cancelado o pagado.

Conservar `estado_legacy` y mapear únicamente la semántica demostrable.

### A14 — Reloj cliente no es fecha servidor

Los timestamps V11 se preservan como dato legacy de origen, nunca como equivalente a la fecha servidor nativa IQ GROWTH.

El importador puede detectar anomalías temporales, pero no reordenar o corregir hechos automáticamente.

### A15 — Idempotencia por snapshot + origen + hash

Se rechaza usar únicamente `hash(num + hora + total + items)` como identidad global.

Estrategia preferida:
- `source_system`;
- `snapshot_id`;
- `source_path`;
- `legacy_key`;
- `payload_hash`;
- mapeo a UUID destino.

Una modificación del mismo objeto entre snapshots debe quedar como evidencia de versiones distintas, no desaparecer por deduplicación semántica.

### A16 — Snapshot debe incluir estado local de terminales

Antes del cutover:
- RTDB completo;
- `vs_stock` por terminal;
- `vs_costos` por terminal;
- carrito debe estar vacío/cerrado;
- hashes, timestamp y terminal de cada export.

### A17 — V11 no posee modo read-only confiable

IQG-001.3 requiere mecanismo explícito de write-freeze durante cutover.

No se adopta aún una implementación específica (`sistema_bloqueado`, reglas RTDB, hosting, cierre operativo, etc.). Codex deberá proponer la opción mínima y verificable; cualquier cambio a producción requiere autorización CEO.

### A18 — Backup antes de tocar legado

Antes de cualquier parche, migración o freeze:
- export completo de RTDB;
- copia verificable fuera de Firebase;
- hashes;
- prueba de restauración cuando sea viable.

### A19 — Separación Core / vertical VANSAM

Se confirma:
- P/M/G, toppings, mitad-y-mitad, recetas y preparación → vertical/configuración;
- tipo salón/llevar/delivery puede representarse como canal/configuración universal sin enum rígido;
- cargo delivery pertenece a la operación, no al perfil permanente del cliente.

## 3. Hallazgos de Claude no adoptados literalmente

1. **`PLAN UNSAFE`**: no se adopta como veredicto final porque Claude no pudo leer los cinco documentos canónicos. Su revisión fue útil como auditoría de origen V11, no como certificación del plan completo.
2. **`total + tarifaDelivery` como ingreso reconstruido**: rechazado por falta de autoridad transaccional suficiente.
3. **parche `sistema_bloqueado` obligatorio**: la necesidad de write-freeze se acepta; la implementación concreta queda abierta.
4. **hash semántico como única idempotencia**: sustituido por snapshot/origen/ruta/hash + mapping.
5. **afirmar que V11 ya perdió datos reales**: no confirmado sin inspeccionar producción; sí existe riesgo estático confirmado de pérdida al editar perfiles.

## 4. Nueva Fase -1 — Estabilización y preservación

IQG-001.3 no puede ejecutar snapshot definitivo hasta completar:

1. inventario de terminales activas;
2. backup/export RTDB pre-cambio;
3. captura localStorage por terminal;
4. decisión sobre mitigación del riesgo CRM;
5. write-freeze verificable para cutover;
6. procedimiento de carrito vacío/pedidos abiertos;
7. hashes y manifiesto de evidencia;
8. prueba del importador sobre fixtures/snapshot no productivo;
9. rollback documentado.

**Recomendación arquitectónica:** nunca mezclar ambas series como si tuvieran igual calidad.
